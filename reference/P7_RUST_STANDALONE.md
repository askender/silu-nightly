## 0. 一句话

把 Rust Oracle 从"钉字节的差分参照"升格为**第三台不依赖 Python 的
完整 Silu 编译器**：前端（已有）+ 全量转换器 + Rust 侧运行时合成
+ clang 驱动。缺口三块：运行时前缀目前是数据快照、转换器只认
语料子集（220 个 bail）、没有驱动/出码层。

## 1. 提出过程（2026-11-09 会话）

三平面代码行数对比 → 用户部分转换 16,245(Python) vs 8,291(Rust)
的差距归因（口径削平 1.68× + 四个结构因素）→ 追问"前缀快照能否
Rust 生成" → 论证"生成前缀 ≠ 完整编译器，且快照现状成本 ≈ 0"
→ 结论：技术可行、先例在手、当前不划算；战略前提变更时才值得
推进 → 应用户要求立此 TODO。

## 2. 现状盘点（全部实测）

### 2.1 三平面规模（v1.18.0）

| 平面 | 前端 | 用户部分转换 | 运行时来源 |
|---|---|---|---|
| Python 主实现 | 1,585（+解释器拖入 1,092） | 16,245（剔注释 13,063） | pyobj_runtime.py **代码合成** 5,002 |
| 自举（Silu） | silu_fe.si 2,183 | flat 12,056（剔注释形态） | flat 内**同一合成代码** |
| Rust Oracle | main.rs 2,509 | silu-conv.rs 8,291（剔注释 7,774） | **数据快照** 9,385（const 9,104 + tagged 281） |

复现：`wc -l` 各文件；注释剔除口径见会话记录（Python 11%、Rust 6%）。

### 2.2 Rust 平面缺口清单

1. **运行时 = include_str! 快照**（silu-conv.rs:18-19）。快照重钉
   流程见 reference/README.md §R2 groundwork：编两个语料文件取公共
   前缀。git 实证重钉点：P2 `37667af`、P5 `22ad013`、panic interning
   `03549f1`。
2. **220 个 `bail()` 拒绝点**。运行时定义了 47 个容器函数，Rust
   转换器只引用 16 个；31 个未引用中经 typed_call.py 实证为语言
   操作的有：`l.pop()` `l.clear()` `x in list` `l[i]=v`(str 路径)
   `del d[k]` `d.pop(k)` `d.setdefault()` `d.clear()`、dict[int,*]
   高级族（rawdict_int_entry/int_slotof）、动态平面互转
   （to_pylist/to_pydict_*）。语料普查：19 文件中这些操作零出现
   （dict[int,int] 仅 dict.si 的 get/set，已钉）。
   复现：`grep -o 'bail("[^"]*")' reference/rust/src/bin/silu-conv.rs
   | sort | uniq -c`；容器差集用 const_prefix.ll 的 define 名单与
   转换器引用名单做 `comm -23`。
3. **无驱动/出码层**：不调 clang、无 .o/链接/执行（README 非目标：
   NOT the product compiler / NOT a bootstrap dependency / NOT shipped）。

### 2.3 快照现状成本 ≈ 0（反推进论据）

`ll conv rustconv` 19/19 是**完整 .ll 连前缀一起逐字节**比对——
Python 侧运行时合成若漂移，门禁立刻红，快照不可能静默过期。唯一
成本 = 输出变化时重钉（分钟级，且此类变化本就受"双实现同 commit"
纪律约束）。

### 2.4 先例：仓库已有一台无 Python 的编译器

自举平面 siluc（C 驱动 + Silu 写的前端/转换器）在无 Python 机器上
即可 .si → 可执行文件，驱动头注释原文 "No Python anywhere"。
**"去 Python 化"不是本事项的增量价值**；Rust 全量化造出来的是
第三台产品编译器。

### 2.5 同步面放大实证（1.16.2→1.18.0 同批输出变化的落地成本）

| 平面 | 增量 |
|---|---|
| Python 原始源 | +170（user-part +80 / runtime +90） |
| flat（剔注释全转换器） | +79（11,977→12,056） |
| Rust | **+409**（7,882→8,291） |

原因：Python 共享发射路径（助手层复用），Rust 逐上下文显式 arm。
W1 落地后运行时同步面从两份变三份，此放大效应是持续成本主体。

## 3. 工作分解（WBS）

### W1 运行时前缀 Rust 生成（~5-6k 行）

- **W1a 合成逻辑移植**：pyobj_runtime.py 5,002 行（剔注释约 4.4k）
  → Rust 约 4-6k。直排发射代码，接近 1:1，量大但机械。
  可行性先例：typed_codegen_flat.si 已用 Silu 语言合成出逐字节
  相同的运行时（pyconv==boot1 全输出一致）。
- **W1b 命名/规范化层移植**（约 1k 行，**雷区**）：NameScope、
  `.N` 去重、空名占槽、结构体常量打印——PROGRESS.md 38+ 条隐式
  规约大半在此。前车之鉴：strbuf 同步时 text 层结构体常量双包装
  bug（对象 repr 进 .ll）。
- **验收**：Rust 生成的 const_prefix.ll / tagged_prefix.ll 与快照
  逐字节一致，新增常驻差分门禁。

### W2 语料外形状补齐（220 bail → 全量或白名单化）

- 分批：容器方法族（§2.2 清单）→ dict[int,*] 高级族 → 动态平面
  互转 → 其余零散（aug/attr/slice/dynamic 各 1-6 处）。
- 每批同步**扩大语料**（新增使用对应操作的语料文件），ll 门禁
  全绿为准。
- 估算：silu-conv.rs 从 8,291 → 约 12-15k 行（Python 全量用户部分
  剔注释 13,063 为上限参照，Rust arm 风格可略省）。

### W3 驱动层（数百行）

clang 子进程调用 + 前缀切分 + 外部声明合成 + LTO 运行时缓存。
参考 tools/siluc_main.c（已有 C 版）；可直接移植，或复用 siluc
驱动形态（它已按"转换器输出全 .ll"接口工作）。

### W4 契约与流程改造

- reference/README.md Oracle 契约重写（"不是产品编译器"三连删除）。
- 纪律修订：输出变化的提案从"双实现同 commit"升级为**三实现同
  commit**（Python + flat + Rust 运行时合成）。
- 重钉流程退役，改为三实现互拍。

## 4. 总账

| 项 | 一次性 | 持续 |
|---|---|---|
| 现状（快照） | 0 | 输出变化时重钉（分钟级/次） |
| 本方案 | W1 ~5-6k + W2 ~+4-6k + W3 ~0.5k ≈ **10-12k 行新 Rust** + 大量对拍迭代 | **每个输出变化同步三份运行时实现**（§2.5 放大效应） |

已排除的中间方案：仅用 Rust 生成前缀做校验门禁（不升格产品）——
同步面照付、快照照留，两头不占。

## 5. 风险与反论

1. **命名层字节细节**（W1b）：全部隐式规约只有差分实证背书，
   无规范文档可依；移植即重新踩一遍所有坑。
2. **三份同步面**：strbuf 单例 +409 vs +79 实证放大 5×。
3. **价值反论**：第三台编译器的增量价值是什么？自举平面已满足
   "无 Python"；Rust 平面当前价值（差分 Oracle）已由快照方案
   以近零成本维持。
4. **范围蔓延**：W2"全量"没有自然边界（Python 转换器随语言演化
   持续增长，Rust 要追着同步全部新形状——即放弃 Oracle 的
   "子集钉死"保护）。

## 6. 推进时机（满足其一才立项）

- **T1 战略变更**：决定把 Rust 平面升格为产品（如对外发布独立
  参考编译器、或 Rust 平面需要独立演化不再跟随 silu 版本钉住）。
- **T2 维护瓶颈**：Python 平面维护成为瓶颈，或目标部署环境
  排斥 Python 工具链且自举平面不可用。
- **T3 语料压力**（可量化）：语料持续加入未钉形状，bail 同步
  成本累计超过 W1+W2 移植成本。观测指标：`git log` 中
  silu-conv.rs 为追形状而改的提交频次与行数。

**反触发**（不构成时机）：快照重钉麻烦（成本 ≈ 0，§2.3）；
"想要无 Python 编译器"（已有 siluc，§2.4）。
