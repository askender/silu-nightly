# Progress and plan (pre-compact checkpoint, 2026-10-16)

## Just landed

**Nested def + lambda** (commit 2d36c2e) with Rust nested-item
semantics across all six surfaces, and **f-string via ir2c** (commit
1fc08ff). Full suite: 955 passed, 2 skipped.

The design, recap: both front ends (Python `ir_generator.py` and the
self-hosted `silu_fe.si`) run an identical hoist pass. Nested defs and
lambdas become module-level functions with mangled path names; closure
capture is a compile error; `self` is the one exception — a hoisted
function touching self gets a leading self parameter, call sites thread
it by fixpoint. Lambdas desugar to a hoisted def plus a `funcref`
node. See `docs/feature_coverage.md` for the six-surface checklist.

Bug fixes along the way (all in the same two commits): ir2c decl dedup
for sibling loops, obj-annotated ann_assign boxing (was a SEGV),
empty-list PObj typing, null-safe pyobj_eq/isinstance in typed LLVM.

### Inheritance finding (needs a decision)

The earlier survey ("6 base methods, inline them") was wrong. Typed
**inherits the base's whole convert() pipeline and boxed PyObject
runtime**: 82 base-owned attributes are read (pyobj_add, dict/list
runtimes, malloc/printf, ...); typed_codegen.py has no convert() of
its own. Inlining = merging silu_ir_to_llvm.py's 4973 lines into the
class. Options:

- (a) port-time merge: typed_codegen.si flattens the used base
  methods; Python sources keep the inheritance (recommended -
  Python stays clean, the merge is mechanical)
- (b) Silu gains single inheritance (not Rust-shaped; rejected)
- (c) Python-side merge now (= the deferred split work, backwards)

## Inheritance decision review (after import landed, 9a0827b)

Cross-file import changes the picture: the .si port is no longer
forced into one file (llvmlite.si imports separately). Three
options for the TypedCodegen(SiluToLLVMConverter) inheritance:

1. Flatten at port time (recommended): a small generator script
   merges the two classes' methods into one .si class
   mechanically. Re-merge = re-run the script, so the "drift"
   cost of flattening disappears; Python sources keep the
   inheritance and the dynamic backend stays untouched.
2. Add class inheritance to Silu: rejected - Rust has none (fragile
   base problem, implementation inheritance couples reuse with
   polymorphism), and it would have to land on six surfaces for one
   use case.
3. Rust-style composition in Python now: the correct end state, but
   it is exactly the deferred P1 refactor (template-method
   inversion of convert(), 82 shared attrs explicit) - largest
   effort, highest risk, and orthogonal to getting the port done.

Plan: option 1 now; option 3 remains the P1 refactor. When it
lands, the flatten script degenerates to a no-op.
