## Inheritance decision review (after import landed, 9a0827b)

Cross-file import changes the picture: the .si port is no longer
forced into one file (llvmlite.si imports separately). Three
options for the TypedCodegen(SiluToLLVMConverter) inheritance:

1. Flatten at port time (recommended): a small generator script
   merges the two classes' methods into one .si class
   mechanically. Re-merge = re-run the script, so the "drift"
   cost of flattening disappears; Python sources keep the
   inheritance and the dynamic backend stays untouched.
2. Add class inheritance to Silu: rejected - Rust has none (fragile
   base problem, implementation inheritance couples reuse with
   polymorphism), and it would have to land on six surfaces for one
   use case.
3. Rust-style composition in Python now: the correct end state, but
   it is exactly the deferred P1 refactor (template-method
   inversion of convert(), 82 shared attrs explicit) - largest
   effort, highest risk, and orthogonal to getting the port done.

Plan: option 1 now; option 3 remains the P1 refactor. When it
lands, the flatten script degenerates to a no-op.

## Native dispatch chain: the class-identity family fixed (2026-10-18)

The `no field 'triple'` module-init panic and the segfault cascade
behind it were all one family: instance class identity did not
survive the compile-time lifetime of a value. The id()-keyed
`_inst_class` dict only knew construction sites and field reads, so
loads, call results and parameters boxed with cid=-1 and the
dispatch chains fell through. Structural fix: the kind string now
carries the class (`"instance:Token"`, mirroring `"func:"+name`),
and `_box` stamps the cid from the kind. The id() dict is gone.

Fixes landed along the chain (each found by the next crash):

- kind carries class: helpers `_inst_kind/_is_inst/_kind_cls/
  _kind_llvm_key`; producers (construct, field read, static call and
  method-call results, funcref calls, params, loop targets, name
  bindings) emit classed kinds; `_declare_var` upgrades from
  `_var_class`; coerce/unbox/is-compare/if_expr/declare sites
  normalize
- `_collect_ctor_returns` sees through `x = Ctor(...); return x`
  (per-function ctor-bind map) - `scope_new()`-style factories then
  class their call results
- `_unbox(obj, INSTANCE)` unwraps tag-6 boxes via
  `pyobj_unwrap_instance` instead of blindly bitcasting (dynamic-ABI
  factories return boxes into instance-typed fields)
- `_emit_dyn_method_call` boxes results BEFORE the merge branch
  (instructions after a terminator produced invalid IR) and no
  longer double-boxes PObj* returns (only raw i8* returns get the
  class-stamped wrap)
- `_emit_dyn_attr_read` stamps instance-field boxes with the
  declared field class (`_fc`), and its no-match path panics loudly
  (with the attr) instead of returning a null box
- dynamic-ABI method bodies class their raw params from
  `_var_class` (method self arrived as a plain INSTANCE slot)
- slices on dynamic containers: `pyobj_list_slice` +
  tag-dispatching `pyobj_slice_any` (the OBJ subscript path passed
  slice nodes through as null keys)
- `str_join_boxed` rewritten as a real two-pass pyobj join (the old
  one bitcast a pylist as a raw str list and copied from past the
  buffer end)
- `pyobj_instance_cid` is tag-guarded (non-instance boxes answer -1
  via a `silu_no_cid` cell; isinstance on a non-instance used to
  dereference garbage)
- dead `silu_dbg_i64` helper removed from every generated module

Mini repro `selfhost/t_gep.si` (imports llvmlite.si, builds one gep)
runs native == interpreter. The full native converter now clears

## 经验沉淀：本项目调试方法论（2026-10-19，compact 前存档）

### 1. 自举暴露的 bug 分类学

自举（用 Silu 编译的转换器再编译 Silu 程序）暴露的缺陷分三类，
判定标准很明确：

- **Python 对象模型掩盖的设计缺陷**：如 `id()` 当编译期身份、
  方法名分派优先级。Python 下从不显形，因为 Python 自己的分派
  不依赖我们生成的 cid 链。修法是把它变成显式类型信息
  （kind 字符串携带类名），不是打补丁。
- **Silu/Python 语义差**：`None.text` 在 Silu 经 shim 得 ""、
  在 Python 抛 AttributeError。这类路径 Python 下不可达，只有
  原生能走到（PointerType(None) 缓存键冲突）。修 twin 时两份
  拷贝必须同步改（twin 字节锁）。
- **新代码真 bug**：如终结符后发指令、PObj* 结果二次装箱。
  特征是 IR 审计能直接看出结构错误。

### 2. 调试工具箱（按可靠性排序）

1. **raise 式诊断（最可靠）**：`raise RuntimeError("DBG ..." + x)`
   走 print+exit 路径，exit 会 flush stdio。**print 到管道不行**——
   全缓冲，SIGSEGV 吃掉缓冲区，什么都看不到。pty（script -q）
   也不行——EOF 语义变化，read_stdin 直接返回空。
2. **__silu_line 全局变量**：编译产物每语句前写行号，崩溃后
   lldb 里 `x/1gx <地址>` 直接读出最后执行的 .si 行。**陷阱**：
   import 拼接保留各文件原始行号——行号 ≤1024 是 llvmlite.si
   的行，不是 flat 文件的行（本轮被坑两次）。地址用
   `nm binary | grep silu_line` 查。
3. **断点命令日志**：`b <fn>` + `breakpoint command add 1` +
   `expr -- (void*)$x0` + `continue` + DONE，比一次性 lldb 表达式
   链可靠（后者常解错地址/偏移，本轮 `cell+48` vs `inst+48`
   误读一次导致整段推理作废）。
4. **探针递增法**：selfhost/t_gep.si 为基座，每次加一两行
   复刻崩溃链，跑 native vs interpret 对拍。**必须先**
   `cp selfhost/llvmlite.si /tmp/llvmlite.si`——/tmp 副本不会
   自动更新（本轮全部 /tmp 探针结果因旧副本作废过一次）。
5. **诊断信息设计**：报"值的来源"比报"值的现状"有用——
   `ptr.opname`（哪条指令产的）、`ptr.type.text`（什么类型）、
   `len(indices)`（哪个调用形态）。gvar/Argument 没有 opname，
   会变成新的 AttributeError。

### 3. 已固化的门禁流程

每个里程碑：改代码 → 门禁（test_llvmlite_text 27 项覆盖四层：
文本层 vs 真 llvmlite 字节一致 / flatten --si 过 check /

### 所有坑的根源总结（用户要求）

11 个跨平面缺陷，归为四个结构性根源（全部是"Python 平面天然
正确、原生平面显形"）：

**根源 A：未处理语法节点静默降级为 null**（贡献最多）
- multi_assign（#9）：链式赋值 `a = b = None` 的存储全部静默跳过
  → 未初始化栈槽读垃圾 → 追了几场的"堆损坏""funcref 盒泄进
  is_null/const_node 槽""cid 之谜"全是它的随机表现。ASan 全绿
  因为不是越界——是合法槽位的合法读，只是没人写过。
- chained_compare（#12）：链式比较恒假（本段）。
- 列表推导式（#5）：原生平面把推导式降级为 null 赋值。
教训：**双平面后端的"unknown op → null"默认路径是系统性盲区**
——任何 IR 生成器会发、而后端不认识的节点都静默产生错误语义。
正确姿势是 unknown op 响亮 panic（当时为了兼容旧代码没改）。

**根源 B：双平面 API 语义分裂**
- str(x.type)（#11）：真 llvmlite str() 得 "i8*"，twin Type 的
  str() 是 repr → self-first 判定恒假 → 分发元数全体偏移。
- %格式化（#4）、Silu 无默认参数（运行时才炸）。
教训：**凡在转换器源里调用 Python 内建（str/len/列表推导/
关键字参数），必须逐一确认 twin 语义一致**；flatten 的元数补全
（NON_BUILDER_RECV 白名单）会把同名方法调用改写——新代码用
`.add(` 必须核白名单。

**根源 C：名字键副作用表跨作用域泄漏**（#8）
- var_class/var_kinds(instance:X)/_list_elem_class 以变量名为键，
  模块级条目经函数作用域拷贝被继承——函数内重绑的同名短名
  （c/b/fn，twin 满篇）拿错类。
- nested_hoist 的 funcref 改写同样作用域盲（#10）：提升函数名
  与局部同名时，局部的每次使用都被改成 funcref 节点。
教训：**任何"按名字查表"的编译期状态都要显式建模作用域**——
Python 的字典语义天然无作用域，而变量名会在嵌套作用域里复用。

**根源 D：真运行时数据结构的边角缺口**
- list_insert 不写 capacity（堆越界写，布局敏感、ASan 掩盖）、
  set.update 路由进 dict 写坏结构、dict.keys/values 路由错、
  list×int 无运行时、jr_number 的 i64 溢出、超大字面量序列化。
教训：这些只在"转换器转换自己"的规模与形态下被踩到——
**自应用是最强的模糊测试**，16 个小程序门禁永远测不到。

**方法论沉淀**（按见效排序）：.ll 手术 printf（tag/表索引/行号
三件套，一轮定身份）> 双平面状态转储对比（推断 sigs/类布局/

## 四管线编译对比 + rustc 缓存查证（2026-10-24，tools/bench_compilers.py）

问题：自举 Silu 编译 0.27-0.32s vs rustc 0.13s——rust 是不是也
吃了缓存？

**rust 缓存查证（实证）**：

- rustc 直调（-C opt-level=3）三连编译耗时恒定
  0.125/0.123/0.122s，编译后磁盘除产物二进制外**零残留**（无
  增量目录、无中间缓存）→ 直调 rustc **没有任何跨次缓存**，
  0.13s 是真实冷编译速度。
- rustc --version 裸进程 48ms：其 0.128s 总耗时约 1/3 是进程
  启动本身。
- 缓存在 **cargo（构建系统层）**：cargo clean 后冷 0.274s vs
  热重建 0.050s（工件级缓存，未变 crate 整体跳过；--release
  profile 不启用 rustc 增量编译）。与我们的运行时 .o 缓存同类
  但粒度更粗（整个 crate vs 共享运行时前缀）。

**四条编译管线**（6 基准，median of 3）：

| 管线 | s/程序 | 进程构成 |
|---|---|---|
| 原版（silu build：py FE + py 码生成 + clang 冷） | 0.577 | 2 |
| 原版 + .o 缓存 | 0.355 | 2 |
| 自举（py FE + fp.bin + clang 冷） | 0.542 | 3 |
| **自举 + .o 缓存（单进程驱动）** | **0.273** | py+fp+clang |
| rustc 直调（无缓存） | 0.128 | 1 |

要点：

- **自举+缓存成为最快的 silu 管线**（0.577 → 0.273，比原版
  Python 编译器快 2.1×）：单 Python 驱动进程做前端+缓存链接
  编排（/tmp/bc_selfbuild.py 模式），fp.bin 只做码生成。
- 码生成阶段本体：native 0.057s vs python 0.208s（3.7×）；
  fp.bin 裸进程开销仅 3ms——0.057s 几乎全是真实转换工作。
- 剩余差距解剖（0.273 vs 0.128）：python 前端进程 0.138s，
  其中 **~0.10s 是 silu.cli 胖 import**（importtime 实测：
  z3+loguru 66ms、symbolic_executor 链 96ms——`silu ir` 根本
  用不到）；clang 用户 .ll -O2 + 链接 ~0.10s；fp.bin 0.057s。
  rustc 单进程做完全部阶段且没有外部运行时需要反复重编。
- 运行面（best of 5）：silu 0.017s ≈ rust 0.016s（1.03×，
  打平），解释器 14.9s（881×）。

后续空间（按性价比，量化）：cli.py 胖 import 懒加载（省
~0.1s/次，最便宜、零风险）；常驻编译 daemon（再省进程启动
+ import + 解析重复）；clang 链接层已接近地板价。

## siluc 单体编译器：一个进程，源码直达 LLVM IR（2026-10-25，v1.6.1）

观察：rustc 也没有 daemon——每次调用都是一次性进程，链接交给
系统工具。所以"像 rustc"的终态不是常驻服务，而是**单体编译器**：
一个进程做解析+降级+码生成。

**撞名审计先行**（48×184 模块级符号）：仅 2 处撞名——const_str
（fe 手改成 fe_const_str）与 main（两侧都撞）。消解方式：主源
去 main 化（工作马函数 fe_compile(src)/conv_convert(ir_json)）+
各自薄 wrapper 出独立二进制（silu_fe_main.si / silu_conv_main.si）；
flat 的 main 从 flatten 模板（flatten_si_tail.si）里改，重生成后
双不动点重验全绿。

**siluc.si = 两个 import + 一行管道**（Silu 的 import 是编译期
文件内联，天然的单体合体机制）：

    import silu_fe
    import typed_codegen_flat
    ...print(conv_convert(fe_compile(src)), end="")

**三方字节等价**（fib/arith/mandelbrot/jsonparse/wordcount）：
siluc 单进程 .ll == fe|conv 双进程管道 .ll == Python 前端+转换器
参考 .ll，逐字节一致。

**速度**：源码→.ll 单进程 67.5ms vs 双进程管道 69.5ms（省的只
是 fe 启动+管道 IO ~2ms，符合预期；大头从来在 clang 与编排）。
完整构建管线（python 编排+siluc+clang×2+运行时 .o 缓存）接入
tools/selfhost_build.py 与 bench。

**形态并存**（按用户要求保留旧管线便于对比分析）：拆分 binaries
（silu_fe/silu_conv wrapper）与 compile_with 三段式留在
tools/selfhost_build.py，不动点测试同时驱动两形态；新增
test_siluc_monolith_matches_split_chain 锁"单体 == 拆分链 == 参考
平面"三方一致。pycompat 垫片升级：先走 silu.importer 的 import
内联展开再 exec，使 wrapper 形态在 CPython 下同样可跑。

**新坑（嵌套 def 参数默认值）**：fe_compile 尾部签名把 stack 等
列表作为**带类型参数的默认值**传入递归函数时，typed 后端按值
装箱语义使子层 append 不可见（与 g_locals 同根）——本轮通过
"外层共享状态由调用方持有、函数内只新建局部"的写法绕开，根治
项与 g_locals 一并列入 todo（object 参数应共享 pyobj 引用）。

**连带修复（单体化的测试面收口）**：

- importer：`fix_missing_locations` 改无条件调用——部分解析的
  import 节点会重建出无位置的 ast.alias，compile() 直接拒绝
  （pycompat 首先撞上）。
- 测试基建四处迁到 wrapper 形态：native parity / 转换器不动点 /
  解释器 parity 都改为构建"flat + wrapper"（flat 本体无 main，
  单独构建出的二进制读 stdin 只会吐空）；m4 的 _fe_ir/pycompat/
  m5 调用补 cwd=源文件目录（stdin 喂入的前端按 **cwd** 解析
  import，参照前端按**文件目录**——语料测试一直是这个约定）。
- round-trip 固定到自包含源：import 展开携带**别的文件**的行号，
  单文件再生成在数学上无法复原（wrapper 排除，自包含的
  silu_fe.si 顶上引导闭环成员位）。
- **ir2c 补 read_file 内建**（fopen/fread 全量读，对齐
  read_stdin_all 形态）——m5 的 ir2c 版前端首次走到 import 展开

  `nm + ".si"` 这类 pyobj 字符串拼接会被推成整数加法）——m5
  的循环保持自包含源范围，动态字符串支持列入 todo。

六程序行为逐一比对一致（含 jsonparse 空 stdin 的报错路径）。
缓存模型原封不动（rt.o 仍是完整一份，剥离发生在最终链接）。

**为什么不做"分类按需缓存"**：按函数族拆多份 .o 只能加速
运行时的**一次性**冷编译（~0.66s，每个转换器版本仅一次），
稳态零收益；而 dead_strip 已给出更细的函数级按需、零架构
改动、不碰前缀不变量。分类拆缓存反而要解决族间内部调用
（pyobj_print→float_repr/rawstr、create_list→rawlist_new…），
复杂度花在没有收益的地方。

**纯静态彻底脱缓存的成本/收益**：dead_strip 后静态程序对缓存
的全部接触 = 链接期扫描 rt.o 符号（毫秒级）。转换器端真静态
模式（普查为 0 则不发射运行时）可把 .ll 从 400KB 缩到 3KB、
跳过拆分与 rt 链接——省 ~10-20ms/次，属美学收益；且
silu_panic 连纯静态也离不开（需单独发射或内联）。按需再排。

## --static 门控：把静默动态回退变成响亮报错（2026-10-25，v1.6.3）

重新评估"纯静态模式"的价值后修正结论：性能收益在缓存管线下
≈0（fib 的 clang 本来就只编译 3KB 用户部分），但**契约价值**
是真的——typed 后端对无法静态化的名字**静默**落到 PyObject
存储（自举攻坚的根源家族正是静默降级），这个门把它变成编译
错误并点名具体符号。

**语义**（silu/static_gate.py）：静态 = 标量（白名单
silu_panic/float_repr/view_ord）+ **类型化**容器（rawstr_/
rawlist_/rawdict_/rawutf8_* 原生结构族）；禁止 = 装箱
（create_*）、动态派发（pyobj_*）、拆箱（unbox_*）、盒装方法
族与转换桥。

**入口**：`silu build --static` 与 `tools/selfhost_build.py
--static`（siluc 路径同样普查）。

**基准分野**（14 个实测）：静态 8 个（fib/arith/float/list/
dict/spectral/trees/nbody——类型化容器全算静态）；动态 5 个
（mandelbrot/jsonparse/knucleotide/wordcount/string）。

**核心演示**（test_the_point_silent_fallback_becomes_loud）：

    x = 1
    x = "s"     # 无 --static：静默编译成 pyobj，正常跑
                # 有 --static：报错并列出 create_int,
                #   create_str, pyobj_print

该门同时是静态子集的回归闸（保护 print 特化一类成果）和
RFC 静态化路线的常新普查。13 项新测试；无 --static 行为
不变。

## match 类模式窄化：Rust 式和类型的"窄化路线"落地（2026-10-25，v1.7.0）

RFC 里暂缓的"sum-type 静态化"拆出了便宜得多的第一步：**不动类
型系统，给 match 的类模式加窄化**。`case JInt(n)` 检查实例 cid
并在臂内以字段**声明类型**绑定载荷——下游算术/字段读取全部落
到静态槽。变体=普通类（构造=普通实例化），双平面天然一致
（pycompat 补 __match_args__，CPython 原生 match 直接跑）。

**实现面**（五面同步）：

- IR：ir_generator 本就发射 match_class 节点（此前执行面拒绝）。
- typed 后端：OBJ 主体放行（类模式/捕获/通配）；cid 条件先分
  支、臂内再取 instance_ptr 装载字段（instance_ptr 无 tag 守卫，
  必须匹配后才可调用）；裸 list/dict 字段 kind None 归一化；
  关键字模式按字段名解析。
- AST 解释器 / IR 解释器：MatchClass 全语义（位置+关键字+精确
  类）。
- silu_fe parse_pattern：类模式解析（位置/关键字），parity 绿。

**顺带抓出两个真 bug**：

1. **IR 解释器捕获作用域**：捕获值被推成内层帧，臂内对外层变
   量的赋值（total += n）写进捕获帧后丢弃——改为按 Python 语
   义绑定进外围帧（空捕获不推帧的老注释只修了一半）。
2. **typed 后端槽分裂（既有 bug，模块级 match 捕获 + 函数同名
   局部）**：模块级捕获把名字放进 _module_vars 名字集，函数内
   对自己第二次声明的"同 kind 复用"被误判为遮蔽模块全局→另开
   新槽——初始化写旧槽、循环用新槽，函数返回 0。纯旧特性即可
   复现（case n + num2 局部 n）。修复=跟踪 _scope_local_vars，
   本作用域自建槽无条件复用；另将作用域入口对重绑名的存储槽
   继承一并清除。

**jsonparse 改写验收**（Rust 孪生同构：JInt/JStr/JArr/JObj 变体
类 + 窄化消费）：三面输出与原版**逐字段一致**
（4498500 3000 22890 3000）；--static 普查 ~30→18 个动态符号，
剩余全部是表示层（容器构造/变体装箱/桥），pyobj_add 等算术派
发清零。**性能如实记录**：74.2ms vs 旧版 74.7ms（1.01×）——
消费端只占 ~4ms，大头在解析循环的逐字符机制（每字符 ~15 层
函数调用：pos[0] rawlist_get + s[i] str_at + digit_value 调用
链），对比 Rust 3.7ms；那是下一个独立战场（游标提升/内联），
不在本轮语言构造范围。

门禁：match_class 六项新测试（含模块级捕获回归锁）、原生
16/16、全量套件见提交信息。

**dual-valid 纪律的三次现形**（本轮收口时全被门禁抓住）：嵌套
函数 raise 内建名被提升器当捕获；dict 推导无 IR 节点（改普通
循环）；`self._scope_local_vars.add(name)` 被 flatten 元数改写
器当 builder 调用补成 3 参（新增属性接收者白名单
NON_BUILDER_ATTR）。cli 兜底 except 的 logger.error(file=) 写法
修为 print（真错曾被 TypeError 掩盖）。

## str 传参借用：jsonparse 78.7→8.3ms（2026-10-25，v1.7.1）

"游标提升/内联"的归因剖析推翻了原假设：游标提升早在位
（list[int] 注解后 rawlist 读写直达），函数调用仅占 2%。逐层
ablation + macOS sample 采样锁定真凶：**rawstr 传参深拷贝**——
`_coerce` 的 RAWSTR→RAWSTR 无条件拷贝被用到了调用参数上，
jsonparse 每次递归 parse 都深拷整个 87KB 文档（2 万 token ≈
4.4GB memmove ≈ 70ms，数字严丝合缝）。

**修复 = 借用传参 + 生命周期规则**：

- 四个调用发射点（方法调用/static/dyn/funcref）RAWSTR→RAWSTR
  参数零拷贝直传；
- 被调方把 str 参数登记为 borrowed：读取自由；`s += x` 重绑
  走 concat 新建（Python 别名语义，b2 探针：h(d)="abx" 而
  d="ab"）；对借用槽的赋值不再 drop 旧缓冲（那是调用方的）；
  函数退出清理跳过未重绑的借用槽；
- 所有权用**双集合**表达（_borrowed_strs 不可变 + _owned_strs
  增量）——`set.discard` 不在 .si 子集，dual-valid 第四次咬人。

**调试过程抓出的隐藏缺陷**：第一个生成器的 raw 参数没登记
borrowed（只补了第二个）→ 被调方退出清理 free 了调用方缓冲
→ 输出空/段错误——最小探针 b1 三语句二分定位。修复后 13 个
基准解释器 vs 编译输出逐一比对全 OK，jsonparse 三方（解释器/
编译/rust 孪生）输出**逐字节一致**。

**性能**：jsonparse 78.7→**8.3ms（9.5×）**，距 Rust 4.4ms 仅
1.9×；原计划的序比较窥孔与单字符融合探针查实**早已存在**
（rawstr_at_cmp_cstr/at_eq_cstr 融合路径完备），无需新做。
全语料实测其余基准无回归（string/wordcount/knucleotide 字符串
大户全部 OK）。

## siluc C 驱动：一行命令，零 Python（2026-10-25，v1.8.0）

    ./siluc file.si -o prog

C 驱动（tools/siluc_main.c，~400 行）完整接管编排：spawn
siluc1（编译器核心，原 siluc 更名）→ 前缀拆分 → 外部声明合成 →
缓存 rt.o → 双 clang。运行时 .o 缓存自举（空程序 probe 得运行
时前缀，剥离 probe 的空 main，符号表提取存 rt.syms）；全局类型
提取到首空格、函数声明 `declare <ret> @name(...)` 对齐
runtime_cache.py；internal→global 可见性提升只在 rt.o 构建期。

**验收**：14 基准产物输出与 Python 管线逐程序一致；jsonparse
含 stdin 全对。**编译 0.136s**（Python 管线 0.178，rustc
0.128——从 1.4× 差距缩到 1.06×，剩下的全在 clang 本体）。
selfhost_build 默认路由过驱动；--save-ll/--static 走 siluc1 拆
分管线。驱动 15 项新测试 + 管线不动点改用 siluc1。

**arena 分配器实测否定**（2c900e5 后补测）：malloc 本身只占
jsonparse 的 ~2%（7ns/次 × 36k 次 ≈ 0.25ms/10.7ms），剩余差距
在 pyobj 派发的每操作常数——根治是路线二，不是分配器。
